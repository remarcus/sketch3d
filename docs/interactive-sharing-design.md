# Public interactive artwork sharing — design draft

## Proposed first release

Share a bounded GLB through an unlisted HTTPS link. The app uploads the exact GLB bytes generated by the existing whole-drawing or selected-strokes exporter; it does not upload the native `.sketch.json`, recovery data, reference-board images, source OBJ files, camera bookmarks, or workspace preferences. The confirmation screen should show the chosen scope, GLB byte size, stroke/material counts, and the fact that anyone with the link can view and download the model.

The desktop app remains the editor. A separate static web viewer loads one GLB, supports orbit/pan/zoom and reset-view controls, and reports loading, unsupported-file, network, and size-limit errors. A 10 MiB upload cap is a proposed initial limit, subject to performance checks on representative mobile devices. The existing 128 MiB exporter limit is too high to adopt as a viewer limit without a separate mobile performance pass.

## Lifecycle and ownership

- **Publish:** user reviews a generated preview and explicit upload summary, then confirms. The service returns a high-entropy unlisted URL and a separate management capability.
- **Update:** user previews the replacement GLB and confirms. The service atomically replaces the content at the existing URL; failed uploads leave the previous revision available.
- **Unpublish:** user confirms removal. The viewer URL stops serving the model immediately; retained backups, logs, caches, and deletion timing must be specified by the chosen host.
- The user owns the artwork and authorizes the service to host only the confirmed GLB. Anyone with the unlisted URL can view and download it. No public directory or search listing is included in the first release.
- Without user accounts, management depends on a locally stored secret capability. It must be stored with restrictive OS file permissions, excluded from drawings and backups by default, and recoverable only while the user retains it. Account-based ownership would need a separate authentication design.

## Service and operational costs

No hosting provider is selected. The service needs bounded object storage, HTTPS delivery, upload rate limits, per-object and per-owner quotas, abuse reporting, TLS/domain renewal, monitoring, and a deletion path. Cost depends on retained bytes, download bandwidth, request volume, and support/abuse handling; a monthly budget and deletion-retention policy must be approved after pricing a concrete provider. Do not enable publishing until those recurring costs and who pays them are explicit.

## Validation before implementation

Choose the host and account/capability model; price the proposed quotas; document retention and cache deletion; validate the viewer and GLB limits on low-end Android/iOS browsers; verify update failure and unpublish behavior; and confirm there is no implicit camera use or upload before the explicit publish action. Publishing remains unavailable until these decisions and tests are complete.
